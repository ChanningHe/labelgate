---
title: 升级到 v0.3
description: 从 Labelgate v0.2 升级到 v0.3 前需要改什么，以及出问题时如何回滚。
---

v0.3 下你的标签照常可用，但升级前有几项设置必须先改好。

## 升级前必做 [#checklist]

1. **镜像标签改成 `v0.3`。** 没有 `latest` 标签，`v0` 也仍然停留在 0.2。

   ```yaml
   image: ghcr.io/channinghe/labelgate:v0.3
   ```

2. **设置 API token。** `api.token`（`LABELGATE_API_TOKEN`）至少 16 个字符。不设置的话，dashboard 和 API 都不会开启。

   ```bash
   openssl rand -hex 32   # 把输出填到 LABELGATE_API_TOKEN
   ```

3. **删掉已移除的配置项**，配置文件和环境变量里都要删：
   - `docker.ssh.*`（`LABELGATE_DOCKER_SSH_*`）以及 `ssh://` 形式的 Docker 地址。改用本地 socket、带 TLS 的 `tcp://`，或在远程主机上运行 [agent](/zh/docs/examples/multi-host)。
   - `db.retention`（`LABELGATE_DB_RETENTION`）
   - `db.vacuum_interval`（`LABELGATE_DB_VACUUM_INTERVAL`）

   只要还留着任何一项，Labelgate 就不会启动，并一次性列出所有问题。

4. **启动 Labelgate，打开 dashboard。** 有报错就逐一修复（参见[下文](#what-changes-you-may-notice)）。

### 如果你在用 agent [#agents]

1. **main 实例和所有 agent 一起升级。** v0.2 和 v0.3 之间无法通信。agent 离线后，main 实例会保留它的记录 24 小时（`sync.agent_grace`），之后就删除。请在这段时间内升级完。

2. **使用足够强的 agent token。** 每个 agent token 至少 32 个随机字符，包括 `agent.agents.<id>.token`、`agent.accept_token`（`LABELGATE_AGENT_ACCEPT_TOKEN`）和 `connect.token`（`LABELGATE_CONNECT_TOKEN`）。

   ```bash
   openssl rand -hex 32
   ```

3. **agent 连接地址必须以 `/ws` 结尾。**

   ```bash
   LABELGATE_CONNECT_ENDPOINT=wss://main.example.com:8081/ws
   ```

4. **自签名证书要配置 CA。** 现在会校验证书。在 agent 上设置 `connect.tls.ca`（`LABELGATE_CONNECT_TLS_CA`）；如果是 main 主动连接 agent（inbound 模式），在 main 上设置 `agent.tls.ca`（`LABELGATE_AGENT_TLS_CA`），指向你的 CA 文件。

5. **agent 的 tunnel 服务要用主机名，需先加白名单。** agent 的 tunnel 服务可以直接指向 IP 地址。如果要用 `http://web:80` 这样的主机名，需要在 main 实例的配置文件里放行：

   ```yaml
   agent:
     agents:
       edge1:
         services: ["web"]
     # 使用 accept_token 连接的 agent：
     accept_services: ["web"]
   ```

   `agent.agents` 只能写在配置文件里。

## 你可能会注意到的变化 [#what-changes-you-may-notice]

- **不再接管已有记录。** 如果某个主机名在 Cloudflare 上已经有 DNS 记录、Access 应用或 tunnel 规则，而且不是 Labelgate 创建的，你会看到 `conflict` 错误，并且什么都不会被修改。v0.2 创建的记录仍然归 Labelgate 管理。参见[所有权与冲突](/zh/docs/ownership)。
- **标签写错现在会报错。** 拼写错误或非法取值（`hostnme`、`proxied: "maybe"`）会显示在 dashboard 和日志里。该服务在 Cloudflare 上已有的资源保持不动，直到你改好标签。
- **默认开启清理。** 容器消失 30 分钟（`sync.remove_delay`）后，Labelgate 会删除它的资源。v0.2 的实际行为也是这样，只是文档写错了。想保留某个服务的资源，加上 `cleanup: "false"`：

  ```yaml
  labelgate.tunnel.web.cleanup: "false"
  ```

- **一个主机名只属于一台主机。** 如果 main 主机或某个 agent 已经在用某个主机名，其他主机再用它就会报 `conflict`。同一个主机名同时配 DNS 服务和 tunnel 服务也算冲突。
- **Access 跟随标签变化。** 从标签里删掉某个邮箱，下一次同步时这个人就失去访问权限。v0.2 创建的共享 Access 策略不会被动，不再需要时请在 Cloudflare 里手动删除。

## 出问题怎么办 [#database-migration]

v0.3 首次启动时会自动升级数据库。升级前，它会先在原数据库旁边保存一份旧数据库的副本：

```
./labelgate-data/labelgate.db.v0.2.bak
```

容器内的路径是 `/app/config/labelgate.db.v0.2.bak`。如果这个文件已经存在，新副本的文件名末尾会加上时间戳。如果副本写不进去（目录不可写或磁盘已满），Labelgate 会直接停止，什么都不改。

回滚到 v0.2：

1. 停止 Labelgate：`docker compose down`。
2. 用备份替换数据库：

   ```bash
   cd labelgate-data
   mv labelgate.db labelgate.db.v0.3
   rm -f labelgate.db-wal labelgate.db-shm
   cp labelgate.db.v0.2.bak labelgate.db
   ```

3. 把镜像改回 `ghcr.io/channinghe/labelgate:v0.2`，agent 也一起回滚，然后执行 `docker compose up -d`。

v0.2 读不了 v0.3 的数据库，所以回滚时一定要恢复备份。
