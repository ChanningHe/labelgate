---
title: 所有权与冲突
description: Labelgate 会动 Cloudflare 上的哪些东西、不会动哪些，以及冲突怎么解决。
---

Labelgate 只修改或删除它自己创建的 Cloudflare 资源。你手工创建的东西它一律不碰。

## Labelgate 会动什么 [#what-labelgate-touches]

| Labelgate 会 | Labelgate 不会 |
|--------------|----------------|
| 按标签创建 DNS 记录、tunnel 规则、Access 应用和策略 | 接管你手工创建的记录、规则或应用 |
| 更新和删除它创建的资源 | 修改或删除不是它创建的任何东西 |
| 往 tunnel 里添加自己的规则 | 改动你自己的 tunnel 规则、兜底（catch-all）规则或 tunnel 的全局设置 |
| 给它创建的 Access 应用加上自己的标签 | 改动不是它创建的 Access 策略，哪怕名字相同 |

Labelgate 这样识别自己的资源：

- **DNS 记录：** 备注以 `labelgate:<实例 ID>` 开头。`comment` 标签的内容会追加在后面。
- **Access 应用：** 带有标签 `labelgate-<实例 ID>`。
- **Tunnel 规则和 Access 策略：** 记录在 Labelgate 的数据库里。

不要手动删掉这个标记或标签。删掉后，Labelgate 就不再管理这个资源，并把它原样留在 Cloudflare 上。

## 实例 ID [#instance-id]

每个 Labelgate 安装都有一个简短的随机实例 ID，例如 `a1b2c3d4`。它在首次启动时生成，保存在数据库里，并打印在启动日志中。因为每个安装只碰带有自己 ID 的资源，所以两个安装可以共用一个 Cloudflare 账户。

除非[数据库丢失](#recovering-from-database-loss)，否则你不需要设置它。

## 已有记录绝不会被接管 [#pre-existing-resources-are-never-adopted]

如果标签里的主机名在 Cloudflare 上已经存在，而且不是 Labelgate 创建的，Labelgate 不会碰它。该服务会在 dashboard 和日志里显示这个错误：

```
conflict: existing record not owned by labelgate
```

Labelgate 每次同步都会重新检查，所以你处理好之后错误会自动消失。

### 怎么解决 [#resolving-a-conflict]

任选一种：

- **交给 Labelgate 管理。** 在 Cloudflare dashboard 里删掉已有的记录、Access 应用或 tunnel 规则。下一次同步时 Labelgate 会创建自己的。
- **保留你自己的。** 删掉这个标签，或者换一个没被占用的主机名。
- **不删除，直接把 DNS 记录交给 Labelgate。** 在 Cloudflare dashboard 里把这条记录的备注改成 `labelgate:<实例 ID>`。下一次同步时 Labelgate 会接管它，并按标签更新。`MX`、`SRV`、`TXT` 和 `CAA` 记录的内容也必须一致。

## 两个服务要同一个主机名 [#conflicts-between-claims]

先用上这个主机名的服务继续保有它。后来者会收到错误，并且不会改动 Cloudflare 上的任何东西：

```
conflict: the A record app.example.com is already managed by container webapp service web on the main instance; remove the duplicate label from one of the containers
```

另外几条规则：

- **一个主机名只属于一台主机：** main 主机或某一个 agent。其他主机会收到 `conflict: hostname app.example.com is already managed by agent edge1`。
- **一个主机名要么用 DNS，要么用 tunnel，不能同时用。** 同一主机名上的 DNS 服务和 tunnel 服务算冲突。
- 同一台主机上的容器，只要记录类型或路径不同，可以共用一个主机名。

要把主机名换到另一台主机上，先在原主机上去掉它。在默认的清理设置下，原主机的记录删除后（大约 30 分钟，`sync.remove_delay`）就会让出这个主机名。

## 你自己的 tunnel 规则 [#coexisting-with-manually-managed-tunnel-ingress]

你可以继续手工管理部分 tunnel 规则。Labelgate 只增删它自己的规则，会保留：

- 你手工添加的规则；
- 兜底规则（如果没有，Labelgate 会加一条 `http_status:404`）；
- tunnel 的全局设置。

如果你的某条手工规则和某个标签用了同一个主机名，这个标签会报 `conflict`，你的规则保持不变。

## Access 应用与策略 [#access-applications-and-policies]

- Labelgate 为每个主机名创建一条 Access 策略，并让它与标签保持一致。从标签里删掉某个邮箱，下一次同步时这个人就失去访问权限。
- 它会把自己的标签加在应用已有的标签旁边。
- 不是它创建的策略，它从不读取、修改或删除。

## 清理 [#cleanup]

- 容器停止或标签被删掉后，Labelgate 会在 30 分钟后删除该容器的资源（`sync.remove_delay`，`LABELGATE_SYNC_REMOVE_DELAY`）。如果容器在此之前回来了，什么都不会删。
- 想把某个服务的资源保留在 Cloudflare 上，给它设置 `cleanup: "false"`：

  ```yaml
  labelgate.dns.web.cleanup: "false"
  ```

- agent 离线时，它的资源会先保留 24 小时（`sync.agent_grace`，`LABELGATE_SYNC_AGENT_GRACE`）。
- 清理只会删除 Labelgate 自己创建的资源。

## 数据库丢失后 [#recovering-from-database-loss]

没有数据库时，Labelgate 会用一个新的实例 ID 启动。它以前创建的 DNS 记录看起来就成了别人的，于是出现冲突。

解决方法：从任意一条记录的备注里找到旧 ID（`labelgate:a1b2c3d4 ...`），在启动 Labelgate 前设置好：

```bash
LABELGATE_INSTANCE_ID=a1b2c3d4
```

这样 Labelgate 会重新接管它的 DNS 记录和 Access 应用。Tunnel 规则和 Access 策略没法这样恢复，请在 Cloudflare dashboard 里删掉旧的。

为了避免这种情况，请备份数据目录（容器内的 `/app/config`）。
