title: Label Format
description: How Labelgate labels work and how to structure them.

Labelgate reads Docker container labels to determine what Cloudflare resources to manage. All labels follow a consistent naming convention.

## Format

```
labelgate.<type>.<service_name>.<property>=<value>
```

| Segment | Description | Example |
|---------|-------------|---------|
| `labelgate` | Prefix (configurable via `LABELGATE_LABEL_PREFIX`) | `labelgate` |
| `type` | Resource type | `dns`, `tunnel`, `access` |
| `service_name` | Unique service identifier | `web`, `api`, `mail` |
| `property` | Setting name | `hostname`, `service`, `type` |

## Service Name Rules

The `service_name` is a unique identifier for each service within a container. It lets you define multiple services on the same container.

**Allowed characters:** lowercase letters, digits, and hyphens: `[a-z0-9]([a-z0-9-]*[a-z0-9])?`

**Reserved words** (cannot be used as service names): `hostname`, `service`, `type`, `target`, `proxied`, `ttl`, `cleanup`, `credential`, `tunnel`, `path`, `origin`, `access`, `default`, `priority`, `weight`, `port`, `flags`, `tag`, `comment`

## Multiple Services

A single container can define multiple services:

```yaml
labels:
  # Service "web" - main website
  labelgate.tunnel.web.hostname: "www.example.com"
  labelgate.tunnel.web.service: "http://app:80"
  # Service "api" - API endpoint
  labelgate.tunnel.api.hostname: "api.example.com"
  labelgate.tunnel.api.service: "http://app:3000"
```

## Strict Validation

Labels are validated when they are parsed. Since v0.3 mistakes are reported instead of being silently replaced by defaults:

- An **invalid value** (a boolean that is not `true`/`false`, a non-numeric `ttl`, an unknown record type, a CAA `tag` outside `issue`/`issuewild`/`iodef`, a port outside 0-65535, a malformed hostname...) **drops that service**.
- An **unknown property** (for example `labelgate.dns.web.hostnme`) is reported as an error; the rest of the service is kept.
- Service names that violate the rules above, or that are reserved, are skipped with an error.

Every label error is logged with the container name and label key, and sets the sync status to `error`, which is shown in the dashboard and in `GET /api/overview`. Check them after changing labels.

## Hostnames

Hostnames are normalised (trimmed, lower-cased, trailing dot removed) and validated. `App.Example.com.` and `app.example.com` are the same hostname.

## Hostname Conflicts

### DNS and Tunnel on the Same Hostname

The same hostname cannot be used both as a DNS record and as a Tunnel ingress rule: a tunnel hostname is served through its own CNAME record. This is a **conflict error** on the service that arrives second, whether the two services are in the same container, different containers, or on different hosts.

```yaml
# WRONG - hostname conflict
labels:
  labelgate.dns.web.hostname: "app.example.com"
  labelgate.tunnel.web.hostname: "app.example.com"  # Conflict!
```

```yaml
# CORRECT - use different hostnames
labels:
  labelgate.dns.legacy.hostname: "old.example.com"
  labelgate.tunnel.web.hostname: "app.example.com"
```

### Existing Owner Wins

When several services claim the same hostname, the service that already owns it keeps it. A newcomer is **rejected** with a stored error such as `conflict: app.example.com|A already claimed by ...`, which is visible in the dashboard and the API. The decision is deterministic and does not flip between sync cycles. See [Ownership & Conflicts](/docs/ownership#conflicts-between-claims).

### Existing Cloudflare Records

If Cloudflare already has a record, Access application or tunnel rule for the hostname that Labelgate did not create, the service reports `conflict: existing record not owned by labelgate` and nothing is modified. See [Ownership & Conflicts](/docs/ownership#pre-existing-resources-are-never-adopted) to resolve it.
