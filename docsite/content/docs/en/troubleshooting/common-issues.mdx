## Conflicts

Conflicts are shown in the dashboard and in `GET /api/resources/*` as resources with status `error` and the reason in `last_error`. They are re-evaluated every cycle and clear on their own once the cause is gone.

### `conflict: existing record not owned by labelgate`

**Problem:** A service stays in the error state with this message.

**Cause:** A DNS record, Access application or tunnel ingress rule with the same identity already exists on Cloudflare and Labelgate does not own it (it has no `labelgate:<instance_id>` comment marker, no `labelgate-<instance_id>` Access tag, and is not tracked as a tunnel rule). Labelgate never adopts or overwrites such resources.

**Solution:** Either delete the existing record or rule in the Cloudflare dashboard so Labelgate can create its own, remove or change the label, or (for DNS records you really want to hand over) add the marker comment yourself. See [Ownership & Conflicts](/docs/ownership#resolving-a-conflict).

### `conflict: ... already claimed by ...`

**Problem:** A container's service is rejected because another one owns the hostname.

**Cause:** The **existing owner wins**. Another container (or agent) already claims that hostname, or uses it as a different kind of record. The first claim stays in place for as long as its owner keeps claiming it.

**Solution:** Use a different hostname, or stop the current owner (or remove its labels) and wait for `sync.remove_delay` to pass: the owner keeps its resources reserved that long in case it comes back. You can find the owner in the error message or in the dashboard.

### `conflict: hostname ... is owned by ...`

**Problem:** A service is rejected although it uses a different record type, path or tunnel than the existing resources on that hostname.

**Cause:** A hostname belongs to one source: the main host or one agent. Another source (`local` or `agent <id>`) has resources on it, including orphaned ones still within `sync.remove_delay`.

**Solution:** Define every service for that hostname on the same host, or free the hostname on the other source first (see [Ownership & Conflicts](/docs/ownership#conflicts-between-claims)).

### `service host ... is not allowed for agents`

**Problem:** A tunnel label on an agent host is rejected, for example for `http://web:80`.

**Cause:** Agent tunnel services must target an IP address, or a host listed in the agent's `services` (`agent.accept_services` for `accept_token` agents). Host names are resolved on the agent host and could reach it or a metadata service.

**Solution:** Add the name, glob, IP or CIDR to the agent's `services` on the main instance, or use the container's IP address. See [SSRF guard](/docs/examples/multi-host#ssrf-guard).

### DNS and Tunnel on Same Hostname

**Problem:** `conflict: hostname app.example.com is used by <owner> as tunnel:<id>` (or as `records` / `cname`).

**Cause:** The same hostname cannot be used for both a DNS record and a Tunnel ingress rule: a tunnel hostname has its own CNAME record.

**Solution:** Use different hostnames for DNS and Tunnel, or only one type per hostname:

```yaml
# Use Tunnel only (recommended for most cases)
labels:
  labelgate.tunnel.web.hostname: "app.example.com"
  labelgate.tunnel.web.service: "http://app:80"
```

## Label Errors

**Problem:** The sync status is `error` and the logs contain a label error with a container name and key.

**Cause:** Labels are strictly validated: invalid values (`proxied: "maybe"`, `ttl: "abc"`) drop the service, and unknown properties (`hostnme`) are errors. Resources that Labelgate already created for a dropped service are held, not deleted, and show `label error: ...` until you fix the label.

**Solution:** Fix the label named in the log line; see [Strict Validation](/docs/labels#strict-validation). If a service is missing without any error, check the key structure: keys that do not look like `labelgate.<type>.<service>.<property>` are ignored silently.

## Dashboard or API Not Available

**Problem:** Connecting to port 8080 fails, or the logs say `api.token is empty: API and dashboard disabled`.

**Cause:** `api.token` is required. Without it the API and the dashboard are not started (reconciliation continues).

**Solution:** Set `LABELGATE_API_TOKEN` to a long random value (`openssl rand -hex 32`), publish the port, and sign in with that token.

## Zone Not Found

**Problem:** The service shows `zone for app.example.com: app.example.com: no matching zone`.

**Cause:** None of the credentials can see the zone containing your hostname, or a `credential` label points at a token that cannot. The zone list of each credential is cached; Labelgate refetches it when a lookup misses, at most once per minute, so a zone you just added can take a minute to appear.

**Solution:**
1. Check your API token permissions in [Cloudflare Dashboard > API Tokens](https://dash.cloudflare.com/profile/api-tokens)
2. Ensure `Zone:Read` permission is granted for the target zone
3. Verify the domain exists in your Cloudflare account

## Tunnel Not Connected

**Problem:** Labelgate creates ingress rules but the hostname returns a 502 or connection error.

**Cause:** The `cloudflared` daemon is not running or not connected to the tunnel.

**Solution:**
1. Check cloudflared is running:
   ```bash
   docker compose ps cloudflared
   ```
2. Check cloudflared logs:
   ```bash
   docker compose logs cloudflared
   ```
3. Verify the tunnel token is correct
4. Check tunnel status in the [Zero Trust Dashboard](https://one.dash.cloudflare.com/) under **Networks > Tunnels**

## Public IP Detection Fails

**Problem:** DNS records with `target=auto` are not being created and the service shows `public IPv4 address: publicip: ...` (or `IPv6`).

**Cause:** Labelgate failed to detect the host's public IP address. It asks `api.ipify.org` and `ipv4.icanhazip.com` (`api6.ipify.org` and `ipv6.icanhazip.com` for `AAAA`). For containers on an agent, the agent's own report is used (`agent <id> reported no public IPv4 address`).

**Solution:**
- Check internet connectivity from the Labelgate container
- Check logs for IP detection errors:
  ```bash
  docker compose logs labelgate | grep "public IP"
  ```
- Use an explicit IP instead of `auto`:
  ```yaml
  labels:
    labelgate.dns.web.target: "203.0.113.1"
  ```

## API Rate Limits

**Problem:** Cloudflare errors with HTTP status 429 in the logs or in a resource's `last_error`.

**Cause:** Cloudflare limits the API to 1200 requests per 5 minutes. Exceeded limits result in a 5-minute ban.

**Solution:**
- Labelgate automatically retries 429 and 5xx responses with exponential backoff (`retry.*`), honouring `Retry-After`, and tries again on the next cycle
- Reduce the number of managed resources if limits are frequently hit
- Avoid rapidly restarting many containers at once
- Increase the intervals to reduce reconciliation frequency (every cycle lists the DNS records of each referenced zone, each tunnel configuration, and the Access apps and policies of each account):
  ```bash
  LABELGATE_DOCKER_POLL_INTERVAL=5m
  LABELGATE_SYNC_INTERVAL=15m
  ```

## Resources Not Cleaned Up

**Problem:** Cloudflare resources persist after containers are stopped.

**Possible causes:**
- The `remove_delay` has not elapsed yet. Orphaned resources are deleted `sync.remove_delay` (default `30m`) after the container is gone. To change the delay:
  ```bash
  LABELGATE_SYNC_REMOVE_DELAY=5m
  ```
- The service has `cleanup: "false"`, so its resources are intentionally kept (they show as `orphaned`).
- Labelgate does not own the resource. It only deletes records with its comment marker, apps with its tag, and rules it tracks. Resources you created by hand are never deleted.
- The resource belongs to an agent that is offline. It is held for `sync.agent_grace` (default `24h`) first.

`cleanup` defaults to **`true`**: if you want to keep resources, set it to `"false"` explicitly:

```yaml
labels:
  labelgate.dns.web.cleanup: "false"
  labelgate.tunnel.web.cleanup: "false"
```

## Resources Deleted Unexpectedly

**Problem:** A record or rule disappeared after a container stopped or an agent went offline.

**Cause:** `cleanup` defaults to `true`. Labelgate deleted a resource it owns after `sync.remove_delay`, or after `sync.agent_grace` plus `sync.remove_delay` for an offline agent. Check that your config does not set `remove_delay: 0s`.

**Solution:** Set `cleanup: "false"` on services that must survive, and raise `sync.agent_grace` if agents are offline for long periods.

## Container Rebuild (Same Config, New ID)

**Problem:** After rebuilding a container, resources show as conflicting.

**Cause:** The new container has a different ID but the same hostname configuration.

**Solution:** Ownership follows the owner key (host or agent, container name and service name), not the container ID, so a rebuilt container with the same name simply keeps its resources. If you renamed the container, the old name stays the owner until it is gone; stop the old container first and the new one takes over on the next sync.

## Agent Connection Issues

### Agent Can't Connect

**Problem:** Agent logs show `connection refused`, `timeout`, a 404, or `unauthorized`.

**Solution:**
1. Make sure the endpoint includes the **`/ws` path**: `wss://main.example.com:8081/ws`. Without it the main returns 404.
2. Verify the main instance is reachable from the agent host and that port 8081 (or your custom `agent.listen`) is open.
3. Check that the agent ID and token match an entry under `agent.agents` on the main instance, or that the main has `agent.accept_token` set. An unknown ID and a wrong token give the same `unauthorized` error on purpose.
4. Agents from v0.2 cannot connect to v0.3; upgrade them (see [Upgrading to v0.3](/docs/upgrading#agents)).

### TLS Certificate Errors

**Problem:** `x509: certificate signed by unknown authority`, or a hostname mismatch.

**Cause:** Certificates are verified by default.

**Solution:** Use a certificate from a trusted CA, or configure your private CA with `connect.tls.ca` (agent dialing the main) or `agent.tls.ca` (main dialing inbound agents). As a last resort for testing, `insecure_skip_verify: true` disables verification; do not use it in production.

### `duplicate_agent`

**Problem:** The agent is rejected after authenticating.

**Cause:** Another agent is already connected with the same ID. The existing session is not disturbed.

**Solution:** Give every agent a unique `connect.agent_id`.

### Agent Services Rejected

**Problem:** An agent's service shows an error such as a hostname or tunnel not allowed, or a service URL rejected.

**Cause:** The claim violated the agent's allow-lists (`hostnames`, `tunnels`, or `accept_hostnames` / `accept_tunnels`), or the tunnel `service` points at `localhost`, a loopback or link-local address, a unix socket or `bastion` (SSRF guard). The stored reasons read `agent <id> may not claim hostname <host>`, `agent <id> may not use tunnel <ref>` or, for the guard, for example `service host "localhost" is not allowed for agents`.

**Solution:** Adjust the agent's entry on the main instance, or use a service address the agent host exposes on a routable address.

### Agent Keeps Reconnecting

**Problem:** Agent logs show repeated connect/disconnect cycles.

**Solution:**
- This is normal during network instability - agents auto-reconnect with exponential backoff, and their resources are held for `sync.agent_grace` meanwhile
- Check main instance logs for authentication errors
- Verify the agent token hasn't been changed on the main instance

## Docker Socket Permission Denied

**Problem:** `permission denied while trying to connect to the Docker daemon socket`

**Solution:** Ensure Labelgate has access to the Docker socket:

```yaml
services:
  labelgate:
    image: ghcr.io/channinghe/labelgate:v0.3
    volumes:
      - /var/run/docker.sock:/var/run/docker.sock:ro
    # Recommended: add the group that owns the socket
    # (stat -c '%g' /var/run/docker.sock)
    group_add:
      - "REPLACE_WITH_GROUP_ID"
    # Or, if you accept the risk, run as root
    # user: root
```

## Startup Errors

**Problem:** Labelgate exits immediately with a `config:` error.

**Cause:** Configuration is validated strictly. Unknown keys, invalid values, and removed v0.2 keys (`docker.ssh.*`, `ssh://` endpoints, `db.retention`, `db.vacuum_interval`) fail at startup.

**Solution:** Fix or delete the key named in the message; see [Removed Keys](/docs/configuration/reference#removed-keys). Fatal errors exit with a non-zero status.

## Database Is Not Writable

**Problem:** Labelgate exits with `open store "/app/config/labelgate.db": ...` (for example `unable to open database file`), or a migration backup fails.

**Solution:** The image runs as a non-root user (UID 65532). The image ships `/app/config` owned by that user, so a Docker named volume is writable automatically. A bind mount keeps the host directory's ownership: make it writable with `sudo chown -R 65532:65532 ./labelgate-data` (or use `user: root`). A named volume created by an older image is root-owned and needs the same treatment. When upgrading from v0.2, the directory also needs free space for the `labelgate.db.v0.2.bak` backup.
