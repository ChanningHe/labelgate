---
title: Ownership & Conflicts
description: How Labelgate marks the Cloudflare resources it owns, what happens on conflicts, and how it coexists with manually managed resources.
---

Labelgate follows one rule: **it never modifies or deletes a Cloudflare resource it does not own.** Everything else on this page is how that rule is enforced.

## Instance ID

Each Labelgate installation has a short random **instance ID** (for example `a1b2c3d4`). It is generated on first start and stored in the SQLite database. Every object Labelgate creates is marked with it, so two Labelgate installations sharing a Cloudflare account do not touch each other's resources.

You normally never need to set it. If you lose the database, you can pin the previous ID with `instance_id` / `LABELGATE_INSTANCE_ID` (see [Recovering from database loss](#recovering-from-database-loss)).

## Ownership markers

| Resource | Owned when... | Marker |
|----------|--------------|--------|
| DNS record | its **comment starts with** `labelgate:<instance_id>` | The marker is written into the record comment |
| Access application | it carries the Access tag `labelgate-<instance_id>` | The tag is created automatically if it is missing |
| Access reusable policy | its ID is recorded on an owned Access row in the database | Cloudflare policies cannot be tagged, so ownership is tracked in the database |
| Tunnel ingress rule | it is tracked in the database by (tunnel, hostname, path) | Rules are not marked; unmanaged rules are identified by *not* being tracked |

### DNS comment marker

A DNS record created by Labelgate gets the comment `labelgate:<instance_id>`. If you set a `comment` label, it is **appended after the marker** and never replaces it:

```yaml
labels:
  labelgate.dns.web.hostname: "app.example.com"
  labelgate.dns.web.target: "203.0.113.1"
  labelgate.dns.web.comment: "main website"
# Resulting Cloudflare comment: "labelgate:a1b2c3d4 main website"
```

The user part is truncated so that the full comment fits in Cloudflare's 100-character limit. If someone removes the marker by hand, Labelgate treats the record as no longer owned: it reports an error for that resource and does not touch the record again.

## Pre-existing resources are never adopted

If Labelgate wants to create a resource and finds an existing one with the same identity that it does not own, it does **not** take it over. The service enters the error state:

```
conflict: existing record not owned by labelgate
```

This applies to manually created DNS records, to Access applications without Labelgate's tag, and to tunnel hostnames that already have an unmanaged ingress rule. The conflict is visible in the dashboard and in `GET /api/resources/*` (`status: error`, reason in `last_error`), and it is retried every cycle, so it clears by itself once you fix it.

### Resolving a conflict

Pick one:

1. **Let Labelgate manage it.** Delete the existing record, application or ingress rule in the Cloudflare dashboard. On the next sync Labelgate creates its own, marked copy.
2. **Keep it yours.** Remove the label, or change the label's hostname to one that is free.
3. **Intentional hand-over of a DNS record.** Add the marker comment yourself (`labelgate:<instance_id> ...`). The record is then recognised as owned and updated to match the labels. This is a deliberate manual act; Labelgate never does it for you.

<Callout type="info">
Objects that carry **your own** instance marker are recovered automatically. If Labelgate crashed between creating a record and saving it, the next cycle finds the marked record and re-attaches it instead of reporting a conflict.
</Callout>

## Conflicts between claims

Two services can ask for the same hostname: two containers, a container and an agent, or a DNS and a tunnel service. Labelgate resolves this deterministically with the rule **the existing owner wins**:

- The first service to claim a hostname keeps it for as long as it keeps claiming it. The claim is persisted, so the outcome does not flap between sync cycles or after restarts.
- A newcomer claiming an already-claimed resource is **rejected**, and the rejection is stored with the reason, for example `conflict: app.example.com|A already claimed by host-b/webapp/web`.
- If nobody holds the hostname yet, ordering is by owner (local containers first, then agents sorted by ID, then container name, then service name), so the result is identical on every run.
- A hostname can only be used in one *class* at a time: plain DNS records, a CNAME, or a tunnel. A DNS service and a tunnel service on the same hostname is therefore a conflict, not just a log line.
- Rejected claims are shown in the dashboard and the API as resources with status `error`. They never create or change anything on Cloudflare.

To hand a hostname over, stop (or remove the labels from) the current owner first. When its resources are orphaned, the next claimant wins on the following cycle. If you switch a hostname from DNS to tunnel (or back) within the same owner, the old record is replaced immediately without waiting for `remove_delay`.

## Coexisting with manually managed tunnel ingress

Cloudflare stores a tunnel's ingress as a single configuration document, so Labelgate edits it with a read-merge-write cycle that preserves what it does not own:

1. Read the live tunnel configuration. **If the read fails, nothing is written.**
2. Remove only the rules Labelgate previously created (tracked in the database).
3. Insert the rules it currently wants.
4. Keep everything else untouched: your manually created rules, the catch-all rule, the global `originRequest`, `warp-routing`, and any per-rule field Labelgate does not model (for example Access validation settings).
5. Write the document back only if it actually changed.

Ordering in the result: Labelgate's exact-hostname rules first (more specific paths before less specific ones), then your unmanaged rules, then Labelgate's wildcard rules, then the catch-all. If the tunnel has no catch-all rule, a `http_status:404` one is added.

If a rule Labelgate wants has the same hostname as one of your unmanaged rules, that service gets the `conflict: existing record not owned by labelgate` error and the unmanaged rule is left alone.

<Callout type="warn">
Cloudflare offers no compare-and-swap for tunnel configuration. A manual edit made in the few milliseconds between Labelgate's read and write can be lost. The window is one API request, and Labelgate only writes when there is a difference.
</Callout>

Tunnel CNAME records (`<tunnel-id>.cfargotunnel.com`) are ordinary owned DNS records. They are created after the tunnel configuration has been written successfully and retried every cycle if they fail. Labelgate does not edit or delete CNAMEs that you created yourself.

## Access applications and policies

- Applications are owned by tag. Labelgate adds the tag to the tags already on the application.
- Policies are created **per hostname** (named `<policy name or app name> (<hostname>)`) and their IDs are recorded in the database. They are updated on every reconcile whenever include, require, exclude, decision or name differ. This is how removing `bob@example.com` from a label really removes his access.
- A policy that Labelgate did not create is never read for matching, adopted, updated or deleted, even if its name matches.
- If updating an application fails, the service goes to the error state. Labelgate never creates a second application as a fallback.

## Cleanup

Cleanup only ever deletes owned resources:

- `cleanup` defaults to **`true`**. When a container stops or its labels disappear, its resources become orphaned and are deleted after `sync.remove_delay` (default `30m`). If the container comes back first, they are reactivated and nothing is deleted.
- With `cleanup: "false"` the resource stays on Cloudflare and is marked `orphaned` in Labelgate. `sync.orphan_ttl` can drop the database row after a while (the Cloudflare object is never touched).
- A record whose marker or tag was removed by a human is dropped from Labelgate's database and left in place, with a warning in the log.
- Access applications and policies follow the `cleanup` setting of the service that references them.
- Resources that belong to an agent that is offline are kept for `sync.agent_grace` first; see [Multi-Host](/docs/examples/multi-host#agent-grace).

## Recovering from database loss

The database holds the instance ID and the ownership records for tunnel rules and Access policies. If you lose it:

- Labelgate generates a **new** instance ID, so its old DNS records (marked with the old ID) look foreign and trigger conflicts. Fix: read the old ID from the comment of one of your records (`labelgate:<old_id> ...`) and set `instance_id: <old_id>` (or `LABELGATE_INSTANCE_ID`) before starting.
- Tunnel rules and Access policies are not marked on Cloudflare, so they cannot be re-attached automatically. Remove the stale rules or policies in the Cloudflare dashboard, or let the conflict errors guide you to them. Labelgate never deletes them on its own.

The upgrade from v0.2 is handled differently; see [Upgrading to v0.3](/docs/upgrading#database-migration).
