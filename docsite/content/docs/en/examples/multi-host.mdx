---
title: Multi-Host (Agent Mode)
description: Deploy Labelgate across multiple Docker hosts using Agent mode, with authentication, TLS and per-agent allow-lists.
---

Agent mode lets you manage containers across multiple hosts. A central **Main** instance handles all Cloudflare API calls, while lightweight **Agent** instances on remote hosts collect container labels and report back.

## Architecture

```
┌──────────────┐     WebSocket     ┌──────────────┐
│   Agent #1   │ ──────────────>   │              │
│  Docker Host │                   │    Main      │ ───> Cloudflare API
│              │                   │   Instance   │
└──────────────┘                   │              │
                                   │              │
┌──────────────┐     WebSocket     │              │
│   Agent #2   │ ──────────────>   │              │
│  Docker Host │                   └──────────────┘
└──────────────┘
```

Agents hold no Cloudflare credentials. They send a full snapshot of their containers and public IP; the main instance validates it against that agent's allow-lists and reconciles it exactly like local containers.

## Connection Modes

### Outbound (Agent connects to Main)

Best for agents behind NAT or firewalls. The agent dials the main instance's `agent.listen` port.

### Inbound (Main connects to Agent)

Best for agents on networks the main instance can reach directly. The agent listens on `connect.listen`, and the main instance dials the agent's `connect_to` URL.

Both modes use the **same handshake and the same security properties**.

## Transport and TLS

- The endpoint is always a WebSocket URL with the **`/ws` path**: `wss://main.example.com:8081/ws`. An endpoint without a path fails config validation with a hint to append `/ws`. The same listener also answers an unauthenticated `GET /health` with `{"status":"ok"}`.
- **Use `wss://` everywhere except on a fully trusted network.** With plain `ws://` the handshake still authenticates both sides (the token is never sent), but the data that follows has no confidentiality or integrity protection. A passive observer would see your container names, labels and public IPs, and an active attacker could tamper with the stream.
- **TLS verification is on by default**, using the system roots or the CA you configure. Agents never silently skip verification any more.
- To trust a private CA, set `connect.tls.ca` (agent dialing the main) or `agent.tls.ca` (main dialing inbound agents).
- `insecure_skip_verify: true` (`connect.tls.insecure_skip_verify` / `agent.tls.insecure_skip_verify`) disables certificate verification. It is an explicit opt-in for testing, logs a loud warning at startup, and should not be used in production.
- Server certificates: set `agent.tls.cert` / `key` on the main instance for outbound agents, or `connect.tls.cert` / `key` on an inbound agent. Alternatively terminate TLS in a reverse proxy that forwards the WebSocket.

## Authentication

Authentication is a mutual challenge-response over the shared token, identical in both modes:

1. The agent sends `hello` with its agent ID and a random nonce.
2. The main instance answers with its own nonce and an HMAC proving it knows the token.
3. The agent verifies that HMAC **before sending anything else**, then replies with its own HMAC.
4. The main instance verifies it and sends `welcome`.

The token itself **never travels on the wire**, so someone who connects to an inbound agent's port learns nothing and receives no data. The connection direction (outbound or inbound) is bound into the HMAC, so a session cannot be relayed from one direction to the other. Tokens are compared in constant time and never logged. An unknown agent ID and a wrong token produce the same `unauthorized` error.

If an agent with the same ID is already connected, the new connection is rejected (`duplicate_agent`) after authenticating, and the existing session stays untouched. Agent IDs must match `^[a-z0-9][a-z0-9._-]{0,62}$` (lower-case; dots are allowed). If you do not set `connect.agent_id`, it is derived from `/etc/machine-id` (first 12 hex characters), falling back to the hostname, lower-cased and sanitized.

Tokens must be at least 32 characters long and contain at least 12 distinct characters (`openssl rand -hex 32` produces a suitable one); repeated or patterned placeholders fail validation. The token never travels on the wire, but a captured handshake can be attacked offline, so a weak token is guessable; high entropy is what protects it.

Before authentication each listener accepts at most 64 pending connections, and at most 4 from one remote address (an IPv4 address or an IPv6 /64). The request headers and the handshake must each complete within 5 seconds.

## Named agents and shared-token agents

**Named agents** are listed under `agent.agents.<id>` and each has its **own token** (recommended):

```yaml
agent:
  enabled: true
  listen: :8081
  agents:
    docker-host-1:
      token: "<output of: openssl rand -hex 32>"
      name: Docker host 1
      default_tunnel: default
      tunnels: [default]
      hostnames: ["*.host1.example.com"]
```

<Callout type="warn">
Labelgate does **not** expand `${VAR}` in config files: a literal `${AGENT_1_TOKEN}` is just a 14-character token and fails the 32-character minimum. Per-agent tokens exist only in the config file (map sections cannot be set through the environment), so write the generated token into the file and keep the file private, or let Docker Compose interpolate it as in the [outbound example](#outbound-mode-example) below. The shared `accept_token` can come from `LABELGATE_AGENT_ACCEPT_TOKEN`.
</Callout>

**Shared-token agents** use `agent.accept_token`: any agent ID that is not listed under `agent.agents` may connect with it. Because the token is a shared secret, anyone holding it can claim any unregistered agent ID, so restrict what such agents may do:

```yaml
agent:
  enabled: true
  # accept_token: set LABELGATE_AGENT_ACCEPT_TOKEN in the environment (>= 32 characters)
  accept_hostnames: ["*.agents.example.com"]
  accept_tunnels: [default]
```

### Allow-lists

| Setting | Applies to | Effect |
|---------|-----------|--------|
| `agent.agents.<id>.hostnames` | one named agent | Glob list of hostnames this agent may claim. Empty = unrestricted (except wildcard hostnames, see below) |
| `agent.agents.<id>.tunnels` | one named agent | Tunnels this agent may target. Empty = only its default tunnel |
| `agent.agents.<id>.default_tunnel` | one named agent | Tunnel used when its labels omit `tunnel` |
| `agent.agents.<id>.services` | one named agent | Tunnel origins allowed beyond IP literals: hostname globs, IP addresses, CIDRs. Empty = IP literals only (see [SSRF guard](#ssrf-guard)) |
| `agent.accept_hostnames` | all `accept_token` agents | Same as `hostnames` |
| `agent.accept_tunnels` | all `accept_token` agents | Same as `tunnels`. Empty = only the global default tunnel |
| `agent.accept_services` | all `accept_token` agents | Same as `services` |

Tunnels are referenced by `default` (the root tunnel), a key of `cloudflare.tunnels`, or a tunnel ID; an unknown reference makes the configuration invalid. A label that omits `tunnel` resolves to the agent's default tunnel (the global default for `accept_token` agents), and that tunnel must be in the allowed list, so an `accept_tunnels` that does not include the global default blocks tunnel labels without an explicit `tunnel`.

Globs use `path.Match` syntax on lower-case hostnames (`*.example.com`). Note that `*` also matches dots: `*.example.com` matches `a.b.example.com`, but not `example.com` itself. A claim that violates an allow-list is rejected with a reason, visible in the dashboard and API; it never reaches Cloudflare.

**Wildcard hostnames** (`*.example.com` as the hostname itself) are allowed for an agent only when its list contains exactly that entry. A glob such as `*` or `*.com` never matches a wildcard hostname, and an empty (unrestricted) list never allows one.

**Agents cannot point CNAMEs at tunnels.** A DNS label of an agent with type `CNAME` and a target under `cfargotunnel.com` is rejected: such a record would route the hostname into a tunnel without the tunnel allow-list. Use a tunnel label instead.

Tunnel resolution for an agent's service: the label's `tunnel` > the agent's `default_tunnel` > the global default tunnel, and the result **must be in the agent's allowed tunnels**.

### SSRF guard

A tunnel service defined by an agent can point cloudflared anywhere, so agent-sourced tunnel services are checked. Only `http`, `https`, `tcp`, `ssh` and `rdp` services (plus `hello_world` and `http_status:<code>`) are accepted; `unix:` / `unix+tls:` sockets, `bastion` and other schemes are rejected. Service URLs with user info (`http://user@host`) are rejected too. The origin host must then be one of:

- **an IP literal** in canonical form that is not loopback, unspecified (`0.0.0.0/8`, `::`), link-local (`169.254.0.0/16`, `fe80::/10`), multicast, broadcast, carrier-grade NAT (`100.64.0.0/10`, which includes the `100.100.100.200` metadata service of some clouds), IPv6 site-local (`fec0::/10`), NAT64 local-use (`64:ff9b:1::/48`), zoned, or an IPv4-mapped, IPv4-compatible, IPv4-translated (`::ffff:0:0:0/96`) or NAT64 (`64:ff9b::/96`) form of such an address. Private LAN addresses (`10.0.0.0/8`, `192.168.0.0/16`, ...) are allowed. Shorthand IPv4 forms such as `127.1`, `2130706433`, `0x7f000001` or `0177.0.0.1` are always rejected;
- **an entry of the agent's `services` allow-list** (`agent.accept_services` for `accept_token` agents): a hostname glob (`web`, `*.svc.internal`), an IP address or a CIDR (`172.20.0.0/16`). An allow-listed entry is accepted even if it is a local address.

Host names are rejected unless allow-listed, because the agent host resolves them: `127.0.0.1.nip.io`, `host.docker.internal` or `metadata.google.internal` would otherwise reach the agent host or a cloud metadata service. To use a Compose service name such as `http://web:80`, add `web` to the agent's `services`:

```yaml
agent:
  agents:
    host1:
      token: "<output of: openssl rand -hex 32>"
      hostnames: ["*.host1.example.com"]
      services: ["web", "api", "172.20.0.0/16"]
```

Local containers (labels on the main host itself) are trusted and are not subject to this guard.

### Agents cannot change local Access policies

Access policy definitions are resolved **within the source of the claimant**: an agent can only reference definitions from its own containers, and can never bind or alter a definition on the main host.

## Agent grace

Agent resources are tied to `last_seen`, which the **main instance** records with its own clock whenever it accepts a report. A disconnect on its own never orphans anything: as long as `last_seen` is within `sync.agent_grace` (default **24h**, at least **5m**), the agent's last reported containers stay desired. An agent that is connected counts as present even if its last report is older than the grace period. The last state of every agent is stored in the database, so restarting the main instance does not orphan agents either.

After the grace period the agent's resources become orphaned and are deleted after `sync.remove_delay` if their `cleanup` is `true` (the default). In the dashboard an agent is `active` (connected), `disconnected` (within grace) or `removed`. If an agent reports that its Docker daemon is unreachable, its last good snapshot is kept and its resources are held.

## Outbound Mode Example

### Main Instance

```yaml
# docker-compose.yaml (main host)
services:
  labelgate:
    image: ghcr.io/channinghe/labelgate:v0.3
    restart: unless-stopped
    volumes:
      - /var/run/docker.sock:/var/run/docker.sock:ro
      - labelgate-data:/app/config
    environment:
      - LABELGATE_CLOUDFLARE_API_TOKEN
      - LABELGATE_CLOUDFLARE_ACCOUNT_ID
      - LABELGATE_CLOUDFLARE_TUNNEL_ID
      - LABELGATE_API_TOKEN
      - LABELGATE_CONFIG=/etc/labelgate/labelgate.yaml
    ports:
      - "8081:8081"   # agent listener
    configs:
      - source: labelgate-config
        target: /etc/labelgate/labelgate.yaml

  cloudflared:
    image: cloudflare/cloudflared:latest
    restart: unless-stopped
    command: tunnel run --token ${TUNNEL_TOKEN}

volumes:
  labelgate-data:

configs:
  labelgate-config:
    content: |
      agent:
        enabled: true
        listen: :8081
        tls:
          cert: /app/config/tls/server.crt
          key: /app/config/tls/server.key
        agents:
          docker-host-1:
            token: ${AGENT_1_TOKEN}
            default_tunnel: default
            hostnames: ["*.host1.example.com"]
          docker-host-2:
            token: ${AGENT_2_TOKEN}
            default_tunnel: default
            hostnames: ["*.host2.example.com"]
```

<Callout type="info">
Docker Compose interpolates `${AGENT_1_TOKEN}` inside `configs.content` when you run `docker compose up`, so the tokens come from your `.env` file. Put the TLS certificate and key in the `labelgate-data` volume (`/app/config/tls/`), or mount them from the host.
</Callout>

### Agent Instance

```yaml
# docker-compose.yaml (remote host)
services:
  labelgate-agent:
    image: ghcr.io/channinghe/labelgate:v0.3
    restart: unless-stopped
    volumes:
      - /var/run/docker.sock:/var/run/docker.sock:ro
    environment:
      - LABELGATE_MODE=agent
      - LABELGATE_CONNECT_MODE=outbound
      - LABELGATE_CONNECT_ENDPOINT=wss://main-host.example.com:8081/ws
      - LABELGATE_CONNECT_AGENT_ID=docker-host-1
      - LABELGATE_CONNECT_TOKEN=${AGENT_1_TOKEN}
      # Private CA for the main's certificate (default: system roots)
      # - LABELGATE_CONNECT_TLS_CA=/certs/ca.pem

  # Your services with labels (same as single-host)
  webapp:
    image: nginx:alpine
    labels:
      labelgate.tunnel.web.hostname: "web.host1.example.com"
      labelgate.tunnel.web.service: "http://webapp:80"
```

The agent's `connect.agent_id` must equal the key under `agent.agents` on the main instance.

<Callout type="info">
The `service` of a tunnel label is resolved by **cloudflared**, not by Labelgate. `http://webapp:80` only works if a cloudflared connector of that tunnel can resolve `webapp`, so run cloudflared on the agent host as well (with the tunnel the agent is allowed to use), or use an address that every connector of the tunnel can reach.
</Callout>

## Inbound Mode Example

### Main Instance

```yaml
# labelgate.yaml (main host; /etc/labelgate/labelgate.yaml inside the container)
agent:
  enabled: true
  tls:
    ca: /app/config/tls/ca.pem   # CA that signed the agent's certificate
  agents:
    docker-host-1:
      connect_to: wss://192.168.1.11:8082/ws
      token: "<output of: openssl rand -hex 32>"   # same value as LABELGATE_CONNECT_TOKEN on the agent
      hostnames: ["*.host1.example.com"]
```

The main verifies the agent's certificate against `agent.tls.ca`, so the certificate must be valid for the `connect_to` host (an IP address such as `192.168.1.11` needs an IP SAN).

### Agent Instance

```yaml
# docker-compose.yaml (remote host)
services:
  labelgate-agent:
    image: ghcr.io/channinghe/labelgate:v0.3
    restart: unless-stopped
    volumes:
      - /var/run/docker.sock:/var/run/docker.sock:ro
      - ./tls:/certs:ro
    environment:
      - LABELGATE_MODE=agent
      - LABELGATE_CONNECT_MODE=inbound
      - LABELGATE_CONNECT_LISTEN=:8082
      - LABELGATE_CONNECT_AGENT_ID=docker-host-1
      - LABELGATE_CONNECT_TOKEN=${AGENT_1_TOKEN}
      - LABELGATE_CONNECT_TLS_CERT=/certs/server.crt
      - LABELGATE_CONNECT_TLS_KEY=/certs/server.key
    ports:
      - "8082:8082"
```

Because authentication is mutual, a stranger who connects to port 8082 gets no token and no data; the agent only talks to a peer that proves it knows the token. Inbound dialers reconnect with backoff, and an agent accepts a newer authenticated main session by closing the older one. An agent's unauthenticated `/health` endpoint returns only `{"status":"ok"}`. With `agent.enabled: true` the main also starts its own `agent.listen` listener, even if all agents are inbound.

## Key Notes

- **Agents are lightweight**: They only collect container labels and report to the main instance. All Cloudflare API calls happen on the main instance.
- **Conflicts**: A hostname belongs to **one source** (the main host or one agent). Claims from any other source on that hostname are rejected, whatever their record type, path or tunnel, and the hostname stays with its source while it has resources there (also during a container restart). See [Ownership & Conflicts](/docs/ownership#conflicts-between-claims).
- **Tunnel assignment**: Container label > agent `default_tunnel` > global default tunnel, limited to the agent's allowed tunnels.
- **Reconnection**: Agents automatically reconnect with exponential backoff if the connection drops, and resources are held for `sync.agent_grace` meanwhile.
- **Upgrades**: v0.2 agents cannot talk to a v0.3 main instance. Upgrade them together; see [Upgrading to v0.3](/docs/upgrading#agents).
